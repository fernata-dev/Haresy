# LIMITATIONS

Read this before quoting any number. Each point below can, on its own, make a conclusion wrong.
(No result numbers are typed here; they live in `results/` and the generated files.)

## 1. The main agent is a simulator, not a model

- `obedient_mock` is a **worst-case simulated agent, not a real model**. It "understands" every
  language and every encoding by reading the attack's ground-truth `intended_call`, which no
  real model has, and then always obeys.
- Consequence: against this agent, a scanner's "attack success" is just its **miss rate** on the
  injection site, and the guard's numbers show what it blocks **when the model is fully
  compromised**. Nothing here says how often a real model follows Egyptian, Arabizi or encoded
  instructions. A real model might ignore a Base64 blob entirely (making encoding "safer" in
  practice) or follow it more often; the simulator cannot tell.
- The simulator's behaviour after an injection is scripted (e.g. exfiltration = read the secrets
  file, then send it). Real attacks and real agents take other paths.

## 2. The real-model pilot was not run

- No model was reachable in the build environment (`results/pilot_status.json`). Every
  real-model question in the research question is **open**.
- When it is run: one model, one date, one quantisation, one prompt format. Models change
  ("model drift"); results do not transfer to other models, versions or system prompts.
  Temperature 0 does not guarantee determinism (hence N=3 repeats); N=3 is a small sample of that
  nondeterminism.

## 3. The data are small, synthetic and (for now) not the student's

- All attack texts in `data/attacks/ai_draft/` are AI drafts, capped at 5 per language by the
  validator (exact counts: `tables.counts` in `results/sim_*.json`). They show the pipeline works. They are **not evidence about Egyptian Arabic**
  or about how people write injections.
- One authored text expands to dozens of cases (encodings × sources × tasks). Those cases are
  **strongly correlated**. Wilson intervals treat them as independent and are therefore too
  narrow. Use the cluster-bootstrap interval (omitted when a cell has < 5 authored texts) and the
  **text-level** McNemar test. Case-level p-values are shown only for completeness.
- The benign set is also small and AI-drafted. A false-positive rate of 0 on it means little; the
  hard benign cases are everyday Egyptian requests the student must collect.
- Dialect labels (`arz` vs `msa` vs `mixed`) are assigned by the author; the validator only checks
  the script. Real code-switching is messier than any label.

## 4. Dev/test leakage risks

- The same AI wrote the dev texts, the test texts, D1's list and D2's lexicon. Even though the test
  texts were committed before the lexicon (tag `data-test-before-lexicon`) and the lexicon
  follows a written provenance rule, the author's knowledge of its own test phrasing may have
  leaked into the lexicon design. This biases D2 **upward** on test.
- The English dev texts contain the exact phrases of D1's list (same author), which makes D1's
  English baseline on dev optimistic. That is why the go/no-go decision uses only the test split.
- After the first test run, D2's reasons on the test base texts were printed to look for code bugs
  (CHANGELOG, "Post-freeze inspections"). No code was changed, but whoever saw them now knows the
  test phrasing. A clean measurement needs a **new** test set written after the next freeze, ideally
  by someone who never saw the lexicon.
- Encoded variants are generated by the same code for dev and test. Tuning D2 on dev encodings
  makes it good at **this project's encoders**, not at encodings in the wild. The `translit`
  encoder and D2's cross-script matching follow the same Egyptian-Arabizi conventions: the
  `translit` cells are optimistic for D2.

## 4b. D6 is not a held-out result

D6 (normalised taint) was designed in m13 after D5-taint's failure on encoded addresses had been
seen on the dev split (m3) **and on the test split** (m6 report). Its test-split numbers are
therefore development numbers in disguise. It also undoes exactly the obfuscations this project's
encoders produce. A clean evaluation of D6 needs a new test set and encodings it was not built for.

## 5. The defenses are simplified on purpose

- D1 is a naive English list; D2 is a hand-written lexicon with proximity rules and a fixed
  threshold. Neither is a trained classifier. "Classifier" defenses are only represented by D3,
  which needs a real model and was not run. D4 needs a locally cached tokenizer and was not run.
- A scanner hit **withholds the whole content**, so a single false positive loses the task. Real
  products may redact instead; utility costs here are a worst case for scanners.
- D5's manifests are written by hand for three toy tasks. Real tasks need richer policies, and
  writing them is the hard part. Blocking every recipient not in the allowlist is why D5 loses
  legitimate delegation ("send a copy to Sara"); a real system would ask the user, which this
  benchmark does not model.
- The taint rule is byte-exact string matching on the attacker-controlled part of the content. It
  is intentionally simple; it misses values that appear only in encoded form, and it would miss
  values the model paraphrases or reconstructs.
- The guard protects **actions**, not **content** or **availability**: in-scope tampering passes,
  and a hijacked agent still fails the user's task. These are reported as residual risk, not hidden.

## 6. The environment is a toy

- Three tasks, five tools, one inbox message, one page, one skill file, fixed carriers in English
  around the payload. Single-turn tasks; no memory, no multi-agent chains, no images, no files
  other than text, no real web.
- Injections are placed in one fixed position of each carrier. Position, length and surrounding
  language were not varied.
- The "Arabic" in carriers (page/email body text) is English; only the payload changes language.

## 7. The skill scanner is not evaluated

- It is checked on synthetic fixtures only. There is no held-out corpus of real skills, so it has
  **no measured detection or false-positive rate**. A clean scan is not evidence of safety.
- It reuses the frozen D2 lexicon, so it inherits all of D2's blind spots (section 4).

## 8. Statistics

- Many cells, many comparisons, no multiple-comparison correction: treat individual "non-
  overlapping" cells with suspicion. The go/no-go rule is fixed in advance in
  `src/hares/eval/report.py::GROUPS`; do not add groups after looking at results.
- N/A cells (an encoding that does not change a script, e.g. leet on Arabic letters) are excluded,
  so pooled "encoded" groups contain different encodings for different languages.

## 9. The Bawwab tool (m8–m10): what is supported and what is NOT covered

**Supported list** (`data/supported_agents.json`, official docs read on 2026-11-17, sources in
`docs/INTEGRATIONS.md`):

| agent | discover | protect mechanisms |
|---|---|---|
| Claude Code | user + project settings, `~/.claude.json` MCP servers (user and local scope), project `.mcp.json`, personal and project skills | PreToolUse command hook (user settings); MCP stdio proxy |
| Gemini CLI | `mcpServers` in user and project `settings.json` | MCP stdio proxy |

**Verified with the real CLIs only for MCP wrapping** (`docs/VERIFICATION.md`): with Claude Code
2.1.326 and Gemini CLI 0.68.0, servers wrapped by `bawwab protect` still start and complete the MCP
handshake (`claude mcp list` / `gemini mcp list`), the clients' requests pass through the proxy, and
`unprotect` restores working configs. **Not verified:** the PreToolUse hook inside a real Claude Code
session, and any model actually calling a tool through the proxy (no model was run; no credentials
were used). Run `bawwab protect --dry-run`, read the diff, and try it on a throwaway account first.

**Not covered at all:** Claude Desktop, Cursor, VS Code / GitHub Copilot, OpenAI Codex CLI, Windsurf,
Cline, Continue, Zed and every other agent (their docs were not reachable or not checked); remote
(HTTP/SSE) MCP servers (cannot be wrapped by a stdio proxy); Gemini CLI built-in tools (no documented
hook was verified); Claude Code project-level settings (only the user settings file gets the hook);
managed/enterprise settings; plugins; MCP resources and prompts (the proxy only checks tools);
anything an agent does without a tool call.

**Platforms.** Paths are home-relative per the docs; only Linux was exercised. macOS and Windows are
untested on real machines (Windows quoting of the hook command is untested).

**Taint mode** (`"destination_mode": "taint"`): a destination is blocked only if it was seen in
untrusted tool output (MCP proxy: that server's outputs and tool descriptions; Claude Code: the
PostToolUse hook records hosts per session). It catches the classic indirect-injection flow (a page
names an address, the agent sends data there) with less breakage than the allowlist, but it misses
destinations the model builds from pieces, and in Claude Code it relies on `session_id` being stable
across hook events (an assumption; not stated in the docs read). The taint store keeps host names,
never content, for 24 hours.

**Policy heuristics are bypassable.** Destinations are found as URLs, e-mail addresses, bare host
names after network commands (curl, wget, …) and in destination-named arguments (url, to, host, …),
also after percent-decoding, Base64-decoding and removing invisible characters; numeric IP forms are
canonicalised and non-ASCII hosts are compared as punycode (look-alikes are never folded into
allowed hosts). They are still missed when assembled at run time (string concatenation in a script,
variables, DNS tricks, other encodings) or when data leaves through an allowed destination.
Secret-path patterns are a short default list. The default allowlist (localhost only) blocks every
other destination, so web-fetching tools stop working until you edit `allowed_hosts`: that is the
cost of the default, not a bug. In-scope tampering (harmful content inside an allowed call) is not
stopped, exactly as for D5 in the benchmark.

**Tool-description scanning inherits D2's blind spots.** Poisoned descriptions are detected with the
frozen Hares scanner, whose attack success on the test split shows it misses wording it was not
built from (see `results/sim_test.json`). A tool that is not hidden is not proven safe.

**Operational risks.** Claude Code rewrites `~/.claude.json` while it runs: quit it before
`--apply`. Wrapped servers start through the Python interpreter that ran `protect`: run
`bawwab unprotect` before uninstalling Bawwab or removing that interpreter, or the servers will not
start. A broken policy file makes the hook deny everything and the proxy refuse to start (fail
closed). The decision log (`~/.bawwab/decisions.jsonl`) records tool names, rules and hosts, but not
arguments.
